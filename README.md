# 本地数值作业与结果归档

在本机运行的数值作业归档：接收有符号 64 位整数序列，计算总和与平方和，
支持作业提交、查询、取消、依赖与结果持久化。

## 能力

- **提交**：记录提交人、幂等请求号、整数序列与种子，接受后返回稳定作业号；
  空序列、引用不存在依赖的提交被拒绝且不产生记录。新作业的默认记录文件名
  已被另一份已恢复作业占用时同样拒绝（见下文“持久化”），不消耗作业号。
- **依赖**：支持一次等待多个上游——提交时给出有顺序的上游作业号列表，
  列表中的作业全部成功且归档完整后本作业才可运行；各上游的总和按列表
  顺序逐个追加到原始序列末尾（不按完成先后改变输入）。列表只能引用提交时
  已存在的作业，不含零与重复作业号；引用已失败/取消的上游仍接受提交，
  但新作业立即失败。单依赖方式继续可用；等待依赖的作业不挡住后面可运行
  的作业。
- **计算**：输出总和与平方和；结果超出 int64 范围时作业失败并说明原因，
  不留下成功结果。依赖作业成功归档后，其总和作为额外整数追加到本次输入末尾。
- **调度**：本地一次只运行一个作业，其余可运行作业严格按提交先后执行；
  等待依赖结果的作业会被跳过，不挡住后面可运行的作业。
- **状态**：区分排队（等待计算位置 / 等待依赖结果）、运行、成功、失败、取消；
  依赖失败或取消会沿链条级联，失败信息指出阻断它的作业。
- **幂等**：请求号在同一提交人内有效；同人同号同内容返回原作业，
  次序/种子/依赖变化返回冲突并保留原记录；并发重复提交只建一个作业。
  提交人与请求号按 Go 字符串的完整字节区分并逐字节持久化，允许包含
  U+0000 及不能组成合法 UTF-8 的字节；重开归档后这类标识仍与提交时
  逐字节一致，不会因落盘被替换成 `�` 而串用记录。
- **取消**：排队与运行中的作业可取消，取消以取消状态成功保存进归档记录为
  生效条件——只有原记录被原子替换为取消记录后才返回成功，返回结果、可查询
  状态与已保存记录始终一致；目录暂时不可写导致临时记录无法创建或原记录无法
  替换时返回实际保存错误，作业保持原状态（继续排队/计算、下游不级联），写入
  恢复后可重新取消。取消后该作业及下游不再产生成功归档；重复取消已取消作业
  仍成功，取消已成功/失败作业返回不能取消且原结果不变。
- **归档**：成功记录保存原始参数、实际参与计算的输入摘要、结果摘要、
  计算日志与校验值；相同有效输入与种子得到相同结果摘要与校验值
  （作业号与时间不参与）。成功状态与完整归档在同一次原子写入中可见。
  重开归档时还会核对实际输入与原始参数、直接依赖数量的对应关系：原始
  序列必须非空且逐项、按原次序出现在实际输入开头，实际输入总长度恰为
  原始长度加直接依赖数量（无依赖时两份序列完全相同）。保存的有序依赖
  列表还必须与提交时遵守同一项唯一性要求：同一作业号出现多次（相邻或
  隔着其他上游）即属于本作业记录自身有误，不论该作业原来排队还是成功，
  重开后一律改判为失败——即使追加值、总和、平方和、日志、摘要与校验值
  全部自洽（重复引用会把同一上游总和追加两次）也不接受；失败原因说明
  依赖列表重复并指出首次再次出现的上游作业号，BlockerID 为 0，被重复
  引用且原本有效的上游保留自己的结果，不被判成失败。原来排队的重复
  依赖作业不能开始计算，原来成功的不能继续返回归档或实际输入；仍在等待
  它的下游按既有规则失败并沿依赖链保留根因（即该重复记录自身）。唯一性
  按作业号判断，两个不同上游总和相同时各引用一次仍然合法。保存的依赖
  列表还必须满足提交时的先后关系：正常提交只能引用已经存在的作业，作业号
  又按接受先后递增，所以每个直接上游作业号都必须严格小于本作业号。引用
  自己或引用后来作业的记录不论排队还是成功，重开后同样一律改判为失败——
  即使被引用作业确实存在且已经成功，本作业的输入、总和、平方和、日志、
  摘要与校验值全部自洽也不接受（例如作业 7 保存对作业 7 自身的依赖，原始
  序列 [0]、实际输入 [0,0] 且全套数值自洽，仍判失败）；失败原因指出保存
  的依赖顺序中第一个作业号不小于本作业的上游，并说明它不能作为本作业的
  上游，BlockerID 为 0，被引用的有效作业保留自己的结果。已因重复依赖判
  失败的记录保留现有重复失败说明（唯一性检查先行）；排队记录改判时补上
  完成时间，原来成功的不返回归档与实际输入，可写时失败结果原样落盘；等待
  它的下游按既有规则失败，根因指向该记录并沿合法依赖链保留。判断先后只
  看作业号，不比较提交时间，也不要求依赖列表按作业号排序（乱序但作业号
  都更小的列表仍按原次序追加各上游总和）；旧的单依赖记录适用同一规则。
  排队记录的原始整数序列同样不能为空：版本、状态与依赖字段合法但原始序列
  缺省、为 null 或为空数组的排队记录，重开后直接判失败——原因说明原始整数
  序列为空，BlockerID 为 0，不开始计算，也不凭已有实际输入或成功上游的
  总和补出原始参数；保留原作业号、提交人、请求号、种子、提交时间与依赖
  顺序，原来没有完成时间的补上进入失败状态的时间，可写时失败结果落盘；
  等待它的下游按既有规则失败，根因沿依赖链保留为该记录自身。空序列指
  没有任何原始整数，[0]、[0,0] 以及含负数或重复整数的非空序列仍是合法
  输入，不按总和是否为 0 判断。已经失败或取消的记录保留原有状态、原因与根因，不因这项检查改写。有依赖的成功
  记录还会核对追加部分：每个直接上游都必须存在、恢复后仍是带完整
  归档的成功状态，且追加值逐项等于这些上游按保存的依赖顺序排列的
  总和（负数、零与上游同和都按位置判断）。另一份输入的
  自洽结果——即使总和、平方和、摘要、日志、校验值随之全部一致，只是
  换了次序或挂在别的参数下——一律改判为失败，失败记录不返回成功归档
  与实际输入，失败原因指出无法对应或无法使用的直接上游作业号；
  仍在等待它的下游按既有依赖失败处理。重开归档时这类失败与正常运行中的
  依赖失败遵守同一项归因规则：失败原因说明当前作业被哪个直接上游阻断，
  BlockerID 则沿依赖链保留最初使结果不可用的根因作业号，不会在每经过
  一个已归档的中间作业时重新起算；直接上游与根因不同时原因中同时说明
  根因作业号，直接上游的记录缺失时以该缺失的作业号为根因并明确说明结果
  无法使用。多依赖作业仍按保存的依赖顺序选取最靠前的不可用上游，再沿
  该上游已有的阻断信息确定根因，其他上游作业号更小或失败原因不同都不
  改变选择。若直接上游全部存在且有效，只是本作业保存的追加输入与上游
  总和不符，则属于本作业自身归档有误，BlockerID 保持 0，不把有效上游
  判成失败或归因给它；作业自身的归档校验失败同样保持 BlockerID 为 0
  并保留具体校验失败原因。按作业号读取与按提交人列举返回一致的归因，
  保存的失败记录保留相同根因。
  保存状态已经是失败或取消的记录重开时不重新判定：状态、失败原因与阻断根因
  原样保留（失败不换成“归档校验失败”等新原因，取消不改判为失败或重新排队），
  只清除终态记录中残留的成功产物——成功归档与实际参与计算的输入；无论记录只
  残留实际输入、只残留归档还是两者都有，残留归档即使数值与校验值全部自洽也不
  能成为恢复为成功的依据。按作业号查看与按提交人列举都只看到原来的失败或取消
  状态，取不到残留的总和、平方和、日志、输入摘要、结果摘要或校验值；可写时
  清理结果经原记录文件原子写回。作业号、提交人、请求号、原始整数及次序（属于
  提交参数，即使原始序列为空也不补造或清空）、种子、有序依赖与已有时间均不变；
  非空请求号仍属于原作业，同一提交人再次提交相同内容返回原终态详情，同样不含
  成功归档与实际输入，不重算、不另建作业；等待这些作业的下游继续遵守既有阻断
  规则。没有残留的失败、取消记录与合法成功记录仍按原规则使用。
  保存状态为排队、原始参数与依赖按现有规则能够正常解析的记录重开时同样先清理
  残留的成功产物：若记录还带有实际参与计算的整数或成功归档，打开时清除这些
  残留——只残留其中一种或两者都有，都按同一规则处理。排队状态继续表示作业尚未
  取得本次成功结果：旧归档中的数值、日志、摘要与校验值即使完全自洽，也不能让
  作业直接成为成功，更不能作为这次计算的输入来源。在作业仍排队或已进入运行、
  但尚未成功归档期间，按作业号查看、按提交人及时间范围列举，以及同一提交人以
  原非空请求号和相同内容重复提交，返回的详情都不含残留实际输入与成功归档；
  原有等待原因与待完成上游仍准确反映当前状态。清理保留原作业号、提交人、请求号、
  原始整数及次序、种子、有序依赖与已有时间，不补完成时间，也不把一个原本合法的
  排队作业改判失败；依赖列表重复、引用不小于自己的上游、原始整数序列为空等排队
  记录自身有误的既有改判规则保持不变。恢复后作业继续按既有调度处理，实际输入
  仅由原始整数和按依赖次序追加的成功上游总和构成；真正成功后详情才出现此次计算
  生成的完整归档（例如原始序列为 [2,-3]、无依赖的排队作业，即使残留一份 [9]
  的旧成功结果，完成后也得到总和 -1、平方和 13，实际输入为 [2,-3]）。清理在
  归档可写时保存到读入的那份正式记录中，非默认文件名不会导致另建记录；清理结果
  暂时无法保存时，仍按既有恢复规则打开归档，本次查询不返回旧产物，写入恢复后
  由后续状态更新或下一次打开完成落盘。
- **查询**：按作业号读取详情，或按提交人与提交时间范围（两端包含）列举，
  起始晚于结束拒绝，结果按提交先后排列；返回数据为拷贝，外部修改不影响记录。
- **持久化**：重新打开目录后，提交、取消与完成结果不丢失，幂等号继续生效，
  排队作业继续处理；上次关闭时仍在运行的作业标记为失败（计算被中断）并阻断下游。
  读取规则接受任何 `job-` 开头、`.json` 结尾的合法记录文件，作业号由记录内容
  识别；单份记录的名称不同于默认命名并不等于存在两个作业。恢复出的记录保持
  读入时的文件名：恢复改写与后续状态更新（运行、完成、失败、取消）都写回原来
  那一份正式文件，不按作业号另写默认命名的记录而同号旧记录原样保留；取消等
  操作以原记录替换成功为生效条件，原文件无法替换时（即使默认命名对应的位置
  可写）返回实际保存错误并保持原状态。新提交的记录仍按默认命名写入。
  当一份已恢复作业的原文件名恰好等于新作业将使用的默认文件名时（例如目录中
  只有作业 1，它却保存在作业 2 的默认命名文件中，新作业拟分配为 2），提交
  功能必须拒绝这次新请求：返回空作业与非空错误（`ErrRecordFileNameOccupied`），
  错误明确说明目标文件已属于另一作业，并给出拟分配的新作业号、被占用的文件
  名和原归属作业号。已有记录即使处于失败或取消状态也不能被当作可覆盖的空位；
  冲突只按记录中的真实作业号判断，文件名中的数字不能替代它。这次拒绝不产生
  新作业、不进入计算队列、不消耗作业号、也不登记提交人的请求号；按作业号
  查询和按提交人列举都看不到被拒绝的请求，也不移动、删除、重命名或改写占用
  该名称的旧记录，旧作业的参数、状态与已有结果（含成功归档的摘要、日志与
  校验值）继续按原有规则读取与保存。名称冲突只影响需要创建记录的新请求：
  相同提交人和非空请求号命中已接受作业时，内容相同仍返回原作业的当前详情，
  内容不同仍返回原有的幂等冲突，不会被这一文件名占用错误替代；空请求号继续
  按新请求处理。关闭归档后把占用名称的旧记录改名为另一个合法且不冲突的文件
  名再打开，此前被拒绝的请求即可作为新请求接受，取得原本未消耗的下一个作业
  号并按正常规则计算、归档；旧作业仍使用它被读取时的文件名更新，新作业仍
  使用默认命名，其他合法的非默认文件名不影响打开和提交。
  一个稳定作业号只能对应一份已保存作业：目录内两份或更多记录文件顶层保存了
  相同作业号（文件名不同、乃至两份内容完全相同）时，打开直接失败并返回非空
  错误（归档对象为 nil），错误说明重复的作业号与至少两份冲突记录的文件名。
  本次打开不启动任何计算，也不改写目录内任何原有记录——中断的运行记录、待
  复查的成功记录、排队与已失败记录都保持原有状态、完成时间、归档与校验值，
  不会先按正常恢复规则改判失败或补写结果再报错；不按时间、状态、排列或完整度
  挑选一份，也不自动换号、合并参数或删除冲突文件。调用方处理冲突后再次打开，
  才按既有规则恢复作业。不同作业号即使整数序列、种子与结果完全相同仍是不同
  作业，不受这项检查影响；原有的解析失败、版本不支持与非法状态错误继续有效。
  两条作业号不同的记录保存了同一提交人和同一个非空请求号时，打开同样直接
  失败并返回非空错误（归档对象为 nil）——提交功能已保证同一提交人的非空
  请求号只对应一个作业，读取保存记录时成立同一项唯一性，不能让两条记录被
  一起接受、再让该请求号静默指向作业号较大的一条。错误说明请求号重复归属
  于不同作业，指出提交人、请求号、至少两个冲突作业号及对应记录文件名。
  即使两份记录的整数序列、种子、依赖与计算结果完全相同也不能合并成一次
  请求；其中一份已经失败或取消也不释放请求号；不按记录状态、提交时间或
  文件排列挑选一条，不自动换号、删除或修补。标识按恢复后的完整字节比较，
  沿用保存格式对非法 UTF-8 字节的恢复含义：含 U+0000 的标识不被截短，
  不同非法字节不因显示成相同替换字符而误报重复；错误中的标识以转义与
  完整字节十六进制给出，不可见或非法字节也能唯一定位。空提交人仍是有效
  标识，但空请求号不启用幂等——同一提交人可以保存多条空请求号作业，不同
  提交人使用相同请求号也正常打开。这类冲突同样在任何恢复改写之前判定：
  本次打开不启动计算，也不改写任何原有作业记录（包括本来会被标记为中断
  失败的运行记录和需要复核的成功归档，状态、完成时间与校验值均保留原样）；
  调用方处理冲突后再次打开，才按既有规则恢复。

## 使用

```go
store, err := numeric.Open("/path/to/archive")
if err != nil { ... }
defer store.Close()

job, err := store.Submit(numeric.SubmitRequest{
    Submitter: "alice",
    RequestID: "req-001",
    Values:    []int64{1, 2, 3, 4},
    Seed:      42,
})
// ...
detail, err := store.Get(job.ID)
if detail.Status == numeric.StatusSucceeded {
    fmt.Println(detail.Archive.Sum, detail.Archive.SumOfSquares)
}
```
